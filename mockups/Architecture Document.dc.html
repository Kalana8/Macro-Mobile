1. Overview

Two client applications share one backend: the Employee App (mobile-first PWA — attendance, audits, checklists, communication) and the Admin Dashboard (desktop web — company/employee management, audit review, checklist assignment, reporting). Both are built on Next.js 16 (App Router), read/write data through Supabase (Postgres + Auth + Storage + Row-Level Security), and use Firebase exclusively for real-time chat/communication.

3. Geofenced Login

Employees can only complete login from within 20 meters of an assigned site. Admin login is exempt (desk-based role).

  1. User submits email/password → Supabase Auth validates credentials, returns session JWT.
  2. Client requests navigator.geolocation.getCurrentPosition() (high-accuracy GPS).
  3. Client fetches the employee's assigned site coordinates (lat/lng, stored per site in Postgres).
  4. Client (or a Supabase Edge Function, for a trusted server-side check) computes distance via the Haversine formula.
  5. Distance ≤ 20m → session is confirmed, attendance clock-in becomes available.
    Distance > 20m or GPS denied → login is rejected with "You must be on-site to log in," session is not finalized.
function withinGeofence(userLat, userLng, siteLat, siteLng, radiusM = 20) {
  const R = 6371000;
  const dLat = (siteLat-userLat) * Math.PI/180;
  const dLng = (siteLng-userLng) * Math.PI/180;
  const a = Math.sin(dLat/2)**2 + Math.cos(userLat*Math.PI/180)*Math.cos(siteLat*Math.PI/180)*Math.sin(dLng/2)**2;
  const d = R * 2*Math.atan2(Math.sqrt(a), Math.sqrt(1-a));
  return d <= radiusM;
}

Enforce the check again server-side (Edge Function) before writing the attendance record — never trust a client-only distance calculation for the authoritative clock-in.

4. Role-Based Access Control

A role column (admin | employee) on the Supabase users table drives access on both the client and the database:

Next.js Middleware
Reads the role claim from the session JWT; redirects employees away from /admin/* routes and admins away from the employee app shell.
Supabase Row-Level Security
Every table (companies, employees, sites, audits, checklists, attendance) has RLS policies scoped by role and company assignment — an employee only ever sees rows for their own company/site, regardless of what the client requests.
UI Gating
Navigation, action buttons, and page components render conditionally per role — belt-and-suspenders on top of middleware + RLS.

5. Data Model (Supabase / Postgres)

Core tables, each with RLS policies keyed on company_id / employee_id:

companies — name, location, visit days/time, status
employees — profile, credentials, role, company_ids[]
sites — company_id, name, address, lat/lng
attendance — employee_id, site_id, clock_in/out, geo-verified flag
audits — company_id, employee_id, main_audits[], sub_audits[], marks, status
checklist_templates — company_id, site_id, main areas + subtasks
checklists — template_id, employee_id, assigned_date, submission (notes/images)
storage: audit-images, checklist-images — Supabase Storage buckets, signed URLs

6. Chat (Firebase)

Chat is the one subsystem on Firebase, chosen for its low-latency real-time listeners:

  • Firestore — conversations/{'{'}id{'}'}/messages collections; client subscribes with onSnapshot for live updates.
  • Firebase Auth bridge — a Supabase Edge Function mints a Firebase custom token from the verified Supabase session, so users sign into Firebase transparently (no second login).
  • Cloud Messaging (FCM) — push notifications for new messages, audit assignments, and checklist reminders when the app is backgrounded.
  • Security rules — Firestore rules check the custom token's company_id/role claims, mirroring the Postgres RLS model.

7. Frontend (Next.js 16)

  • App Router route groups: (app) for the employee PWA shell, (admin) for the dashboard — separate layouts, shared design system.
  • Server Components fetch initial data (companies, assigned sites, audits) directly via the Supabase server client; Server Actions handle mutations (clock in/out, submit checklist, assign audit).
  • Client Components own the geolocation check, live chat subscriptions, and interactive forms.
  • Middleware enforces auth + role redirects on every request before rendering.
  • PWA manifest + service worker on the employee app for install-to-home-screen and offline shell caching.

8. Request Flow — Employee Clock-In

  1. Employee opens app → Next.js middleware verifies Supabase session, role = employee.
  2. Server Component loads assigned site + coordinates.
  3. Client requests GPS position; Haversine check runs against site coordinates.
  4. If within 20m: Server Action writes an attendance row with geo_verified: true.
  5. If outside 20m: Server Action rejects the write; UI shows "move closer to the site."

9. Security Notes

  • All authoritative checks (geofence distance, role, company scoping) are re-validated server-side — the client-side result is UX-only, never trusted for the write.
  • RLS policies are the single source of truth for data access, independent of what the UI requests.
  • Firebase custom tokens are short-lived and re-minted per session; Firestore rules enforce the same company/role scoping as Postgres.
  • Images (audit/checklist attachments) are stored in private Supabase Storage buckets and served via short-lived signed URLs.

Appendix C — Connecting App ↔ Dashboard & Granting Access

There is no direct app-to-dashboard link — everything routes through Supabase, and access is granted by the Admin, not self-service.
How they connect
  1. Admin (in the Dashboard) registers a company, then registers an employee and sets their login email + password, then assigns that employee to one or more companies.
  2. That write lands in the shared Supabase employees table — nothing is pushed to the app directly.
  3. When the employee opens the app and logs in, Supabase Auth checks the same credentials the Admin created.
  4. The app reads the employee's row (via RLS) to know which companies/sites they can see — this is the entire "connection": a shared source of truth, read differently by each client.
  5. Anything the Admin does afterward (assign a checklist, send audit results, add a company visit day) is just another row written to the same tables, which the employee's app picks up via a live Supabase subscription.

In short: the Admin Dashboard is the only place access is granted. The Employee App has no admin functions and cannot elevate its own permissions — it only ever reflects what Supabase RLS allows for that employee's row.

Configurable roles (Roles & Access page)

Access is not hardcoded to just "Admin" and "Employee." The Dashboard has a dedicated Roles & Access page where an Admin defines named roles (e.g. Admin, Supervisor, Field Employee) and, per role, toggles exactly which Dashboard pages and which App pages that role can open — some roles legitimately need both surfaces (a Supervisor, for example, can review audits and attendance in the Dashboard while also clocking in and completing checklists in the App).

  • Each employee record carries an access_role_id referencing one role.
  • Next.js middleware reads the role's toggle set (mirrored server-side) and redirects away from any Dashboard or App route not enabled for that role.
  • Supabase RLS still enforces company/site data scoping underneath the role's page-level access — role controls which pages, RLS controls which rows.
  • Sidebar/bottom-nav items render only for pages the current role has enabled.
